# legal-rag

面向法律条文的法律问答工具。

给它一个问题，它会先从法条库里检索出相关条文，再让大模型**只依据这些条文**作答，并附上条文出处，方便核对。

检索部分目前还是**关键词匹配**，语义检索在路上；生成部分已接入 DeepSeek。RAG 的两个部分都在动，还没走完后半程——见 [路线图](#路线图)。

---

## 为什么做这个

法律文本的特点是高密度、强引用、要求准确。

直接拿大模型问法条，最典型的问题是**编造条号**——它能流畅地说出「根据《民法典》第 XXXX 条规定」，而那条根本不存在。对法律场景来说，这种错误比答不出来更糟。

可靠的做法是反过来：**先把准确的条文检索出来，再交给模型**，让模型只负责解释和归纳，不负责回忆。这样每句话都能追溯到出处。

这个项目做的就是这条链路：**先检索，再作答**。模型不负责回忆条文，只负责解释检索到的那几条。

### 已知局限

**整句提问检索不到条文。** 现在用的是子串匹配——`/ask?q=处理个人信息需要满足什么条件` 会因为整串没出现在任何条文里而命中 0 条，模型只能答「检索到的条文中没有相关规定」。换成关键词（`/ask?q=敏感个人信息`）就正常。

这不是 bug，是关键词检索的固有边界，也正是下一步要做语义检索的原因。

> **关于法条数据**：当前 11 条为**演示数据**，尚未逐条核对。用于验证检索链路，**不构成任何法律意见**。

## 快速开始

环境要求：JDK 21 或更高。

### 1. 配置 API key

`/ask` 接口需要一个大模型，本项目用 [DeepSeek](https://platform.deepseek.com/)（便宜、国内直连、OpenAI 兼容）。

key **不写在配置文件里**——本仓库是公开的，提交真实 key 等于把账户余额送人。改成从环境变量读：

```bash
# macOS / Linux
export DEEPSEEK_API_KEY="sk-你的key"

# Windows（setx 写进用户环境变量，设完要新开终端才生效）
setx DEEPSEEK_API_KEY "sk-你的key"
```

> key 缺失时应用**启动就会失败**，报 `DeepSeek API key must be set`。这是 Spring AI 自动配置的硬性校验，不是本项目的限制。
> 只跑 `/search`（纯检索，不调模型）也仍然需要这个 key，因为装配阶段就会校验。

### 2. 启动

```bash
git clone https://github.com/wangmlandzhaoyj/legal-rag.git
cd legal-rag

# macOS / Linux
./mvnw spring-boot:run

# Windows
mvnw.cmd spring-boot:run
```

启动后访问 <http://localhost:8080>

## API

### `GET /ask?q={问题}`

**核心接口。** 先检索相关条文，再交给大模型，要求它只依据这些条文回答。

```bash
curl "http://localhost:8080/ask?q=敏感个人信息"
```

```json
{
  "question": "敏感个人信息",
  "answer": "根据《个人信息保护法》第二十八条，敏感个人信息是指一旦泄露或者非法使用，容易导致自然人的人格尊严受到侵害或者人身、财产安全受到危害的个人信息，包括生物识别、宗教信仰、特定身份、医疗健康、金融账户、行踪轨迹等信息，以及不满十四周岁未成年人的个人信息。处理敏感个人信息应当具有特定的目的和充分的必要性，并采取严格保护措施。",
  "sources": [
    {
      "law": "中华人民共和国个人信息保护法",
      "articleNo": "第二十八条",
      "content": "敏感个人信息是一旦泄露或者非法使用……"
    }
  ]
}
```

`answer` 是模型生成的，`sources` 是本次实际检索到的条文原文。**两者要对照着看**——`sources` 为空时，模型应当明确回答「检索到的条文中没有相关规定」，而不是用记忆里的法条补上。

### `GET /search?q={关键词}`

只做检索，不调模型。按关键词匹配，命中**法律名称、条号或条文正文**任意一处即返回。

```bash
curl "http://localhost:8080/search?q=个人信息"
```

```json
[
  {
    "law": "中华人民共和国个人信息保护法",
    "articleNo": "第一条",
    "content": "为了保护个人信息权益，规范个人信息处理活动，促进个人信息合理利用，根据宪法，制定本法。"
  }
]
```

### `GET /articles`

返回全部已加载的法条。

### `GET /health`

探活，同时返回已加载的法条条数。

```json
{ "status": "ok", "articleCount": 11 }
```

## 项目结构

```
src/main/java/com/legalrag/
├── LegalRagApplication.java      # 启动类
├── LawArticle.java               # 法条数据模型（record）
├── LawArticleRepository.java     # 数据加载 + 检索逻辑
├── SearchController.java         # /search、/articles、/health
└── AskController.java            # /ask：检索 + 大模型作答，含系统提示词

src/main/resources/
├── law-articles.txt              # 法条数据
└── application.properties        # 模型配置（key 走环境变量，不落文件）
```

`AskController` 里的 `SYSTEM_PROMPT` 是这个项目最核心的东西——它把「法律场景不能容忍编造」这条业务约束，翻译成了模型能执行的四条规则（只依据给定条文、必须标条号、查不到就说查不到、不给法律意见）。

**法条数据格式**（`law-articles.txt`），一行一条：

```
法律名称|条号|条文内容
```

以 `#` 开头的行是注释。

## 设计取舍

第一版**故意**不上数据库，也不上向量库：数据放内存，检索用子串匹配。

理由：这个阶段的目标是把**链路**跑通，不是把**架构**做完美。引入 SQLite 要配 DataSource，引入向量库要装服务——这些都是可能卡住半天的失败点，而对当前目标毫无帮助。

好在数据层是可替换的：只要 `LawArticleRepository.search()` 的签名不变，上层代码一行都不用改。

演进路径（检索侧）：

```
内存子串匹配  →  SQLite FTS5  →  embedding + 向量检索
   现在            下一步              再下一步
```

生成侧已经接上大模型（`/ask`），但**它的上限被检索侧卡着**：检索给什么，模型就只能答什么。所以下一步的重点仍是把检索做准。
